## 1. Схема таблиц (ER-модель)

### 1.1. Таблица `users` (Пользователи)
Хранит учетные данные и персональную информацию.

| Поле | Тип данных | Описание | ИБ-аспект |
|------|------------|----------|-----------|
| `id` | SERIAL PRIMARY KEY | Уникальный идентификатор | - |
| `role` | VARCHAR(20) | Роль: 'guest', 'client', 'manager', 'admin' | Контроль доступа (RBAC) |
| `login` | VARCHAR(50) UNIQUE | Логин для входа | - |
| `password_hash` | VARCHAR(255) | Хэш пароля | **Bcrypt/Argon2** (с "солью") |
| `full_name` | VARCHAR(100) | ФИО клиента/сотрудника | - |
| `phone` | VARCHAR(20) | Номер телефона | **Шифрование (cryptography/Fernet)** |
| `passport_data` | TEXT | Паспортные данные (для договора) | **Шифрование (cryptography/Fernet)** |
| `created_at` | TIMESTAMP | Дата регистрации | - |

### 1.2. Таблица `dresses` (Каталог нарядов)
Основная бизнес-сущность.

| Поле | Тип данных | Описание | ИБ-аспект |
|------|------------|----------|-----------|
| `id` | SERIAL PRIMARY KEY | Уникальный идентификатор | - |
| `name` | VARCHAR(100) | Название модели | - |
| `description` | TEXT | Описание, материалы | Защита от XSS при выводе |
| `size` | VARCHAR(10) | Размер | - |
| `price_per_day` | DECIMAL(10, 2) | Стоимость проката в день | - |
| `status` | VARCHAR(20) | 'available', 'rented', 'maintenance' | - |

### 1.3. Таблица `appointments` (Записи на примерку/прокат)
Связывает клиента, наряд и дату.

| Поле | Тип данных | Описание | ИБ-аспект |
|------|------------|----------|-----------|
| `id` | SERIAL PRIMARY KEY | Уникальный идентификатор | - |
| `user_id` | INT REFERENCES users(id) | ID клиента | Проверка прав (клиент видит только свои) |
| `dress_id` | INT REFERENCES dresses(id) | ID наряда | - |
| `appointment_date` | DATE | Дата примерки или проката | - |
| `status` | VARCHAR(20) | 'pending', 'confirmed', 'completed', 'canceled' | - |

### 1.4. Таблица `defects` (Учет дефектов)
Фиксирует состояние наряда при выдаче и возврате.

| Поле | Тип данных | Описание | ИБ-аспект |
|------|------------|----------|-----------|
| `id` | SERIAL PRIMARY KEY | Уникальный идентификатор | - |
| `appointment_id` | INT REFERENCES appointments(id) | ID связанной записи | - |
| `description` | TEXT | Описание повреждения | Защита от XSS |
| `severity` | VARCHAR(20) | 'minor', 'major', 'critical' | - |
| `created_by` | INT REFERENCES users(id) | ID менеджера, зафиксировавшего дефект | Неотказуемость (Non-repudiation) |
| `created_at` | TIMESTAMP | Дата и время фиксации | - |

> **ИБ-ограничение:** Менеджерам запрещена операция `DELETE` для этой таблицы. Только `INSERT`.

### 1.5. Таблица `deposits` (Учет залогов) – **КРИТИЧЕСКАЯ ДЛЯ ИБ**
Обеспечивает финансовый контроль и целостность данных.

| Поле | Тип данных | Описание | ИБ-аспект |
|------|------------|----------|-----------|
| `id` | SERIAL PRIMARY KEY | Уникальный идентификатор | - |
| `appointment_id` | INT REFERENCES appointments(id) | ID связанной записи | - |
| `amount` | DECIMAL(10, 2) | Сумма залога | **Шифрование (cryptography/Fernet)** |
| `action_type` | VARCHAR(20) | 'hold' (прием), 'return' (возврат), 'withhold' (удержание) | - |
| `prev_deposit_id` | INT REFERENCES deposits(id) | Ссылка на предыдущую операцию (для цепочки) | **Контроль целостности (Blockchain-like)** |
| `transaction_hash` | VARCHAR(64) | SHA-256 хэш текущей записи | **Гарантия неизменности данных** |
| `created_by` | INT REFERENCES users(id) | ID менеджера | Неотказуемость |
| `created_at` | TIMESTAMP | Дата и время операции | - |

> **Механизм контроля целостности:**  
> 1. Записи в таблице `deposits` **никогда не обновляются (`UPDATE`) и не удаляются (`DELETE`)**.  
> 2. Любое изменение (возврат или удержание) создает **новую строку** с `action_type` и ссылкой `prev_deposit_id`.  
> 3. Поле `transaction_hash` вычисляется как `SHA-256(id + appointment_id + amount + action_type + prev_deposit_id + secret_salt)`. Это позволяет в любой момент проверить, что история залогов не была подделана задним числом.

### 1.6. Таблица `audit_logs` (Журнал безопасности)
Регистрирует все критические действия в системе.

| Поле | Тип данных | Описание | ИБ-аспект |
|------|------------|----------|-----------|
| `id` | SERIAL PRIMARY KEY | Уникальный идентификатор | - |
| `user_id` | INT REFERENCES users(id) | Кто совершил действие | - |
| `action` | VARCHAR(50) | Тип действия (напр., 'LOGIN_FAILED', 'DEPOSIT_CREATED') | Мониторинг инцидентов |
| `target_table` | VARCHAR(50) | Затронутая таблица | - |
| `ip_address` | VARCHAR(45) | IP-адрес клиента | Расследование инцидентов |
| `timestamp` | TIMESTAMP | Время события | - |

## 3. Выбранные инструменты защиты (согласно заданию)

1. **Flask-SQLAlchemy**: ORM для параметризованных запросов (защита от SQL-инъекций).
2. **Flask-Bcrypt**: Хеширование паролей с "солью".
3. **cryptography (Fernet)**: Симметричное шифрование ПДн и сумм залогов "на лету" перед сохранением в PostgreSQL.
4. **Flask-Login**: Управление сессиями, декоратор `@login_required`.
5. **Flask-WTF**: Защита HTML-форм от CSRF-атак.
6. **hashlib**: Вычисление `transaction_hash` для контроля целостности залогов.
